# Executive Summary

This audit inspected the active Operations Command Centre V2 route at `app/operations-v2.tsx`, its component set under `src/components/operations-v2`, the state hook `src/hooks/useOperationsCommandCentre.ts`, the calculation layer `src/utils/operationsCommandCentre.ts`, and the services that load or generate telemetry.

The OCC is not currently a fully live operational intelligence centre. It is a hybrid dashboard:

- It reads some genuine database records from Supabase: `transfers`, `execution_sessions`, `treasury_liquidity_snapshots`, and `route_operational_events`.
- Several displayed numbers are calculated from those records on the client.
- Some records are generated by deterministic simulation logic rather than live provider, bank, treasury, or rail feeds.
- One external FX API is live: Frankfurter GBP rates.
- Treasury feed cards from `getLiveTreasuryFeeds()` are hard-coded static corridor intelligence while marked with `health: "live"`.
- Realtime execution subscription is explicitly disabled in diagnostic mode.
- OCC Nexus AI mission summary generation is bypassed before calling the Edge Function. Displayed AI commentary is therefore local fallback telemetry commentary, not live AI output.
- The Provider Sandbox is explicitly labelled `MOCK` and is entirely demonstration intelligence.

Founder answer: the Operations Command Centre is currently displaying **partially simulated operational intelligence**, leaning toward demonstration intelligence. It is not primarily genuine live operational intelligence.

Estimated provenance split:

| Category | Estimate | Rationale |
| --- | ---: | --- |
| Genuine operational data | 20% | Supabase transfer/session records, local QA logs, and external Frankfurter FX rates are real data reads, subject to scope and freshness limitations. |
| Derived operational data | 35% | KPIs, corridor rows, treasury summary, mission status, service health, and fallback mission summary are calculated from available records. |
| Simulated/demo data | 45% | Treasury scores originate from static profiles, route events are explicitly `SIMULATED`, treasury live feeds are hard-coded, provider sandbox is mock, and realtime/AI are disabled or bypassed. |

# Formula Analysis

## Treasury Score

Source: `src/lib/treasuryIntelligence.ts`.

The treasury score is produced when routes are evaluated, then persisted into `treasury_liquidity_snapshots`.

Formula:

```text
treasuryScore =
  clamp(
    corridor.availableCapacityScore * 0.38
    + partner.availableCapacityScore * 0.32
    + rail.availableCapacityScore * 0.30
    - pressurePenalty * 0.45
  )
```

Inputs:

- Corridor capacity score from `CORRIDOR_LIQUIDITY_PROFILES`.
- Partner capacity score from provider-name rules.
- Rail capacity score from rail rules.
- Pressure penalty from corridor, partner, and rail pressure.
- Amount thresholds determine whether a route is normal or high value.
- RLUSD rail capacity uses `simulatedRlusdBalance / liquidityRequiredRlusd`.

Weighting:

- Corridor: 38%.
- Partner: 32%.
- Rail: 30%.
- Pressure penalty: subtracts 45% of aggregate pressure penalties.

Assumptions:

- Corridor liquidity profiles are hard-coded.
- Partner liquidity is inferred from provider display names.
- Fiat rail score is fixed at 84.
- Unknown corridors default to conservative fixed values.

Fallback:

- Unknown corridor: capacity 76, pressure MEDIUM.
- Unknown provider: normal score 84, large-transfer score 76.

Classification: **RED/AMBER**. The score is database-persisted but originates from static simulation assumptions, not treasury balances or partner liquidity APIs.

## Corridor Health

Source: `buildCorridorRows()`.

Formula:

```text
group snapshots by corridor
latest = newest snapshot
previous = second-newest snapshot or latest
trend = latest.treasury_score - previous.treasury_score
capacity = round((corridor_capacity_score + partner_capacity_score + rail_capacity_score) / 3)
pressure = getOverallOperationalPressure(latest)
status =
  HEALTHY if treasury_score >= 82 and pressure != CRITICAL
  DEGRADED if treasury_score >= 65
  AT_RISK otherwise
```

Inputs:

- `treasury_liquidity_snapshots`.

Assumptions:

- The latest persisted snapshot represents current corridor health.
- Capacity can be represented as an equal average across corridor, partner, and rail.

Fallback:

- No snapshots -> no corridor rows.

Classification: **AMBER/RED**. It is derived from records, but those records are generated from static treasury intelligence profiles.

## Overall Operational Pressure

Source: `getOverallOperationalPressure()`.

Formula:

```text
componentPressure = max(weight(corridor_pressure), weight(partner_pressure), weight(rail_pressure))
scorePressure =
  CRITICAL if treasury_score < 55
  HIGH if treasury_score < 70
  MEDIUM if treasury_score < 82
  LOW otherwise
overallPressure = max(componentPressure, scorePressure)
```

Weighting:

- LOW = 1.
- MEDIUM = 2.
- HIGH = 3.
- CRITICAL = 4.

Classification: **AMBER/RED** due to simulated treasury inputs.

## Treasury Utilisation and Available Capacity

Source: `buildTreasurySummary()`.

Formula:

```text
avgCapacity = round((corridor_capacity_score + partner_capacity_score + rail_capacity_score) / 3)
utilisation = 100 - avgCapacity
availableCapacity = max(0, 100 - utilisation)
```

Inputs:

- Latest treasury snapshot.

Fallback:

- No snapshots -> utilisation 0, available capacity 0, pressure LOW, forecast "No treasury telemetry yet".

Classification: **AMBER/RED**. Calculated, but not backed by live balances or real partner capacity.

## Currency Distribution

Source: `buildTreasurySummary()`.

Formula:

```text
amountByCurrency = sum(transfers.senderAmount grouped by senderCurrency)
percentage = round((amount / total) * 1000) / 10
top 5 by amount
```

Inputs:

- `transfers` rows loaded for the authenticated user and account/persona scope.

Fallback:

- No transfers -> empty or zero-percentage distribution.

Classification: **GREEN/AMBER**. It is a genuine calculation from persisted transfers, but only from the limited loaded sample.

## Transfers 24h and Delta

Source: `buildKpis()`.

Formula:

```text
current = transfers where createdAt >= now - 24h
previous = transfers where now - 48h <= createdAt < now - 24h
delta = current.length - previous.length
```

Inputs:

- `transfers`, limited to 25 recent rows.

Fallback:

- No rows -> 0.

Classification: **GREEN/AMBER**. Genuine records, but limited sample and client clock.

## Success Rate

Source: `buildKpis()`.

Formula:

```text
terminalCurrent = execution_sessions where state in (COMPLETED, FAILED) and updated_at >= now - 24h
successRate = completed terminalCurrent / all terminalCurrent * 100
```

Critical issue:

- The hook calls `loadRecoverableExecutionSessions()`, which explicitly filters out `COMPLETED` and `FAILED`.
- Therefore the success-rate formula expects terminal sessions, but the data loader excludes them.

Fallback:

- No terminal sessions -> 0%.

Classification: **RED**. Formula is coherent, but current data loader makes the displayed value operationally invalid.

## Settlement Time

Source: `buildKpis()`.

Formula:

```text
completedCurrent = terminalCurrent where state == COMPLETED
settlementSeconds = average(max(0, updated_at - created_at)) / 1000
```

Critical issue:

- Same loader mismatch as Success Rate: completed sessions are not loaded.

Fallback:

- No completed sessions -> `--`.

Classification: **RED**.

## Treasury Capacity KPI

Source: `buildKpis()`.

Formula:

```text
latestSnapshots = newest 10 treasury snapshots
avgCapacity = average((corridor + partner + rail capacity) / 3)
previousCapacity =
  if latestSnapshots.length > 4, average of snapshots from index 4 onward
  else avgCapacity
capacityDelta = avgCapacity - previousCapacity
```

Classification: **AMBER/RED**. Calculated from DB snapshots, but snapshot source is simulated profile logic.

## Active Alerts

Source: `buildKpis()`, `ActiveAlertsCard`.

Formula:

```text
activeAlerts = events where status != RESOLVED
CRITICAL = severity FAILOVER or DEGRADED
WARNING = severity WATCH
INFO = severity INFO
highestSeverity = max severity by weight
```

Inputs:

- `route_operational_events`.

Critical issue:

- `buildRouteOperationalEvent()` sets every event status to `SIMULATED`.
- Healthy events include `Math.random()` for degradation score.

Classification: **RED** for operational validity, despite being database-backed.

## Operational Health

Source: `buildServiceHealth()` and `OperationalHealthCard`.

Formula:

```text
routingStatus = OFFLINE if criticalAlerts > 1, DEGRADED if warningAlerts > 0, else HEALTHY
treasuryStatus = OFFLINE if treasuryPressure CRITICAL, DEGRADED if HIGH, else HEALTHY
fxStatus = HEALTHY if fxFeedCount > 0 else OFFLINE
marketStatus = HEALTHY if marketOpenCount > 0 else DEGRADED
aiStatus =
  if aiEnabled and missionSummary exists -> HEALTHY
  if aiEnabled and loading -> DEGRADED
  if aiEnabled and no summary -> OFFLINE
  if disabled -> DEGRADED
executionStatus = HEALTHY if realtimeStatus == Live else DEGRADED
notificationStatus = DEGRADED if criticalAlerts > 2 else HEALTHY
```

Assumptions:

- Alerts are a proxy for network status.
- Treasury pressure is a proxy for liquidity service health.
- Any open market is enough to mark markets healthy.
- Notification service health is inferred from alert count rather than notification delivery telemetry.

Classification: **AMBER/RED**.

## Nexus AI Mission Summary

Source: `useOperationsCommandCentre()` and `NexusAISummaryCard`.

Intended flow:

- Build AI telemetry.
- Call `generateIntelligenceReport()`.
- `generateIntelligenceReport()` calls Supabase Edge Function `nexus-ai`.
- If unavailable, use deterministic fallback.

Actual OCC V2 flow:

- The effect logs `mission summary effect bypassed` and returns before calling `generateMissionSummary()`.
- The card therefore uses `buildFallbackSummary()` when dashboard data exists.

Fallback formula:

- Count corridor statuses.
- Count alerts and critical alerts.
- Read treasury pressure/utilisation.
- Count service health statuses.
- Extract KPI values for success and transfers.
- Assemble fixed sentence templates.

Classification: **RED for AI-generated commentary**, **AMBER for local telemetry commentary**.

## Provider Sandbox

- Hard-coded user/account IDs.
- Hard-coded source amount 500.
- Hard-coded destination amounts.

- Mock providers.

Classification: **RED/MOCK**, but clearly labelled as such in the UI.
