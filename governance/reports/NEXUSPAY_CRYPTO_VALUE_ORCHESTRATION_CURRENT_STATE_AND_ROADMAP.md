# NexusPay Crypto Value Orchestration: Current State and Roadmap

## Purpose

NexusPay is intended to let a sender choose how value is funded while allowing the recipient to choose how value is received. Bank transfer and card are funding mechanisms for fiat; they are not separate value types. Crypto is an additional funding or destination value type.

## Current Position After Phase 1

- Yapily provides authenticated sandbox open-banking funding evidence.
- Airwallex provides authenticated sandbox beneficiary validation and bank-payout evidence.
- XRPL Testnet settlement keys now remain in Supabase Edge Function secrets; mobile-device wallet signing has been removed.
- Two backend wallets are funded with Testnet XRP and have active trustlines to Ripple's official Testnet RLUSD issuer.
- NexusPay queries the Testnet ledger for wallet state, reserves and fees, and uses `ripple_path_find` for an executable XRP-to-RLUSD path for the requested amount.
- A genuine `1 RLUSD` Testnet path payment validated with `tesSUCCESS`; the durable request was replayed without creating a second transaction.
- The canonical route engine exposes XRPL only when the current path, trustlines, spendable XRP and fee evidence can support the requested Testnet amount.
- Card funding is disabled because no evidence-backed card tokenisation/acquiring provider is configured.

## Terminology

- **Fiat:** Government-issued money such as GBP, USD, PHP or MYR.
- **Bank transfer:** A mechanism for funding or receiving fiat.
- **Card:** A mechanism for funding fiat, normally linked to a bank or card issuer.
- **Crypto funding:** Value supplied from a customer-controlled wallet or exchange account.
- **Trustline:** An XRPL account-level permission to hold a specific issued token from a specific issuer. It does not transfer funds or give the issuer control of the wallet.

## Phase 1: XRPL Testnet and RLUSD

Phase 1 moves XRPL signing to a secured backend boundary, creates funded Testnet source and destination wallets, establishes Ripple Testnet RLUSD trustlines, obtains an executable Testnet path and executes genuine RLUSD Testnet payments. NexusPay uses Testnet XRP and the current XRP-to-RLUSD path rather than fabricating a faucet balance.

The canonical route engine will use:

- `TESTNET`: wallet balances, trustline state, reserve, ledger index, network fee, path quote and transaction result from XRPL Testnet.
- `LIVE`: the existing live GBP/USD reference FX feed when available.
- `DERIVED`: the Testnet RLUSD amount calculated from the live GBP/USD reference rate.
- `UNAVAILABLE`: missing trustlines, insufficient faucet RLUSD, unavailable network evidence or unsupported execution.

Phase 1 proves blockchain orchestration. It does not prove that real GBP was commercially converted into RLUSD because Yapily sandbox funds and Testnet XRP/RLUSD have no monetary value.

## Phase 2: Non-Custodial Crypto and Fiat Orchestration

Phase 2 introduces regulated provider-generated executable quotes and deposit instructions for:

- Crypto or stablecoin to recipient bank account.
- Bank or card funded fiat to a recipient crypto wallet.
- Crypto to crypto wallet.

For crypto-to-bank payments, the deposit address should normally be generated by the regulated conversion/off-ramp provider. The sender transfers from their own wallet or exchange account; the provider confirms, converts and pays out. NexusPay orchestrates the journey without controlling customer private keys or holding customer crypto.

For crypto-to-crypto payments, the destination address belongs to the recipient and no fiat off-ramp is required.

## Provider Accounts

Phase 1 requires no Bridge, Circle or Fireblocks account.

Phase 2 requires commercial and compliance onboarding with at least one regulated conversion/off-ramp provider. Candidates for due diligence include Ripple for RLUSD and Bridge or Circle for stablecoin-to-fiat flows. Fireblocks is primarily wallet and transaction infrastructure and does not by itself replace the regulated conversion, payout and compliance provider. Provider availability, licensing, supported countries, custody model, sandbox capability and pricing must be verified before implementation.

## Target App Experience

Funding choices should be presented as:

- Bank transfer
- Card
- Crypto

The route engine must compare only executable provider quotes. Each route should disclose the source asset, exact amount required, conversion rate, blockchain fee, provider fee, payout fee, recipient amount, quote expiry, provider, network and provenance.

## Control Principles

- No fabricated prices, balances, fees, liquidity or success statuses.
- No mobile storage of backend settlement wallet seeds.
- No route approval without current mandatory evidence.
- Provider and blockchain idempotency for every submission.
- Persistent evidence and canonical status mapping.
- Explicit `LIVE`, `SANDBOX`, `TESTNET`, `DERIVED` and `UNAVAILABLE` labels.
- Production crypto activity requires legal, regulatory, safeguarding, AML, sanctions and Travel Rule review.
